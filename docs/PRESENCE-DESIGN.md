# Presence Design — opencode Discord Rich Presence

> **Status**: design source-of-truth. Captures the intended presence engine (identity, tool-activity
> resolver, MCP as first-class, random phrases, telemetry) plus **verified Discord constraints**.
> **Reality-checked against**: [`DISCORD-RPC.md`](./DISCORD-RPC.md) (official docs + library sources).
> **Implementation**: deferred to `SCAF-004`. This document is documentation-first per user request.
> **Related**: [`ARCHITECTURE.md`](./ARCHITECTURE.md) · [`CONFIGURATION.md`](./CONFIGURATION.md).

---

## 1. Core concept

Discord Rich Presence represents the **live activity of the opencode agent** — not a static status.
`state` changes dynamically based on the **tool the agent is currently using**, including built-in
opencode tools, custom tools, and MCP tools.

```
OpenCode Events
       ↓
Tool Activity Resolver
       ↓
Activity + Target + Random Phrase
       ↓
Presence Formatter
       ↓
Discord Rich Presence
```

## 2. Presence mapping

| Discord field | Source | Purpose |
|---|---|---|
| `name` | User configuration (best-effort) | Agent identity, e.g. `J.A.R.V.I.S.` — see §16.1 |
| `type` | User configuration | Default `Playing` (0) |
| `details` | OpenCode session title | Active session title |
| `state` | Active tool activity | Tool/action currently running |
| `party` | TODO progress | Work progress (semantic hack — see §16.3) |
| `timestamps` | Session start | Session duration |
| `large_image` | User configuration | Artwork identity |
| `large_text` | Project + model | Metadata tooltip |
| `small_image` | Tool/status | Activity icon |
| `small_text` | Agent/status | Activity detail |

## 3. Identity

Identity is configurable and independent of the literal name "opencode".

```json
{
  "identity": {
    "name": "J.A.R.V.I.S.",
    "type": "Playing",
    "largeImage": "jarvis",
    "largeText": "J.A.R.V.I.S. • AI Coding Assistant"
  }
}
```

The user may rename to `FRIDAY`, `HAL 9000`, etc. The presence engine stays the same.

> **Constraint**: the top line Discord renders is `<Verb> <AppName>`, where `AppName` is the
> registered Discord Application name. `identity.name` maps to `activity.name` and is **best-effort**
> — see §16.1.

---

## 4. Session title

`details` is the **opencode session title**, taken from the session (not re-generated by the engine).

```
Refactor authentication architecture
```

Rendered presence:

```
Playing J.A.R.V.I.S.
Refactor authentication architecture
Editing src/auth/service.ts • Shaping the code
```

If the session title changes, `details` follows automatically.

## 5. Tool activity

`state` represents the **currently active tool**. Generic labels such as `Thinking`, `Coding`,
`Working` are forbidden — activity must derive from the real tool.

### 5.1 Tool sources

```
Tool Activity
│
├── Built-in
│   ├── read, edit, write, bash, grep, glob, lsp, patch, todo, task, ...
│
├── Custom
│   ├── user-defined tools
│   └── plugin tools
│
└── MCP
    ├── GitHub, Playwright, PostgreSQL, Filesystem, Browser, ...
    └── arbitrary MCP servers
```

MCP is a **first-class activity**, not a fallback or secondary category.

### 5.2 Built-in tool mapping

| Tool | Dynamic state |
|---|---|
| `read` | `Reading auth.service.ts • Tracing the code` |
| `edit` | `Editing auth.service.ts • Shaping the code` |
| `write` | `Writing auth.service.ts • Building the next piece` |
| `bash` | `Running pnpm test • Let the terminal cook` |
| `grep` | `Searching the codebase • Following the trail` |
| `glob` | `Exploring project files • Finding the pieces` |
| `lsp` | `Analyzing symbols • Connecting the dots` |
| `patch` | `Applying patch • Making the changes` |
| `todo` | `Updating TODO • Planning the next move` |
| `task` | `Delegating task • Splitting the workload` |

Raw tool names are never shown — the resolver produces human-readable activity.

### 5.3 MCP tool mapping

MCP tools are processed **generically**; unknown servers need no engine update.

```
mcp__github__search_code        → GitHub • Searching repository • Following the trail
mcp__github__create_pull_request → GitHub • Creating pull request • Shipping the changes
mcp__playwright__browser_navigate → Playwright • Opening browser • Exploring the interface
mcp__postgres__query            → Postgres • Querying database • Digging into the data
```

Resolver input/output:

```ts
// input
{ source: "mcp", tool: "mcp__github__search_code" }

// normalized
{ source: "mcp", provider: "GitHub", tool: "search_code",
  action: "Searching repository", phrase: "Following the trail" }
```

Unknown provider/tool fallback:

```
MCP • Running search_code • Connecting the dots
```

## 6. Unified tool activity model

All tools normalize to one model:

```ts
interface ToolActivity {
  source: "builtin" | "custom" | "mcp";
  provider?: string;
  tool: string;
  action: string;
  target?: string;
  phrase: string;
}
```

Examples:

```ts
{ source: "builtin", tool: "edit", action: "Editing",
  target: "src/auth/service.ts", phrase: "Shaping the code" }

{ source: "mcp", provider: "GitHub", tool: "search_code",
  action: "Searching repository", phrase: "Following the trail" }
```

### Resolver flow

```
OpenCode Tool Event
        ↓
Identify source (builtin / custom / MCP)
        ↓
Extract provider → action → target → phrase
        ↓
ToolActivity
        ↓
Presence State
```

## 7. Random phrase system

Random phrases are a **personality layer**, not the primary activity.

Format:

```
<Activity> • <Random Phrase>
```

Pools (seed set; extensible):

| Category | Phrases |
|---|---|
| Reading | `Tracing the code`, `Reading between the lines`, `Following the dependency trail`, `Exploring the implementation` |
| Coding | `Shaping the code`, `Sculpting the architecture`, `Making the changes`, `Building the next piece`, `Turning ideas into code` |
| Terminal | `Let the terminal cook`, `Command line sorcery`, `Executing the plan`, `Talking to the shell` |
| Searching | `Following the trail`, `Connecting the dots`, `Looking for the missing piece`, `Exploring the codebase` |
| Documentation | `Looking beyond the code`, `Consulting the archives`, `Searching for answers`, `Checking the documentation` |
| MCP | `Connecting external systems`, `Talking to the tools`, `Bridging the gap`, `Calling in reinforcements`, `Working across the stack` |

Phrase rotation is gated by `phraseCooldownMs` (§15) so personality never feels like spam.

---

## 8. Context telemetry

Format:

```
150.4K (57%)
```

Not `Context 57%`. Full combined format: `150.4K (57%) • TODO 4/9`.

- `150.4K` — context tokens currently used.
- `57%` — percentage of the context window used.

```
context_percentage = used_context_tokens / context_window_tokens × 100
```

The percentage must use the **actual context window / model limit**. If context data is unavailable
for a given event, use the **last known value**, never `0%`.

---

## 9. TODO telemetry

```
TODO 4/9
```

= `4 completed / 9 total`, sourced from `todo.updated`. TODO is **additional telemetry**, not the
primary state.

---

## 10. Model / agent / project metadata

Metadata does not occupy the main activity lines — it goes into tooltips:

```
large_text: agentic-crm • DeepSeek V4 Flash
small_text: build agent • GitHub MCP
```

This keeps the presence clean while technical info stays available on hover.

## 12. Event priority

When several events arrive nearly simultaneously:

```
ERROR
  ↓
PERMISSION
  ↓
MCP / TOOL
  ↓
FILE
  ↓
THINKING
  ↓
IDLE
```

Tool activity is the primary state while a tool executes; after the tool ends, fall back to the
previous agent activity.

## 15. Configuration & timing

```json
{
  "identity": {
    "name": "J.A.R.V.I.S.",
    "type": "Playing",
    "largeImage": "jarvis",
    "largeText": "J.A.R.V.I.S. • AI Coding Assistant"
  },
  "presence": {
    "showSessionTitle": true,
    "showContext": true,
    "showTodo": true,
    "showModel": true,
    "showAgent": true,
    "showProject": true,
    "showTimestamp": true,
    "randomPhrases": true,
    "showMcpProvider": true
  },
  "behavior": {
    "updateDebounceMs": 750,
    "phraseCooldownMs": 5000,
    "idleTimeoutMs": 30000
  }
}
```

> **Canonical names**: the JSON above uses vision keys. Canonical option names, the new `activityType` / `phrases.*` / `presence.show*` options, and the reconciliation table live in [`CONFIGURATION.md §3f–3g`](./CONFIGURATION.md#3f-presence-engine) and [`ARCHITECTURE.md §5.1`](./ARCHITECTURE.md#5-config-schema).

**Debounce** — never `event → Discord update` per event. Coalesce:

```
event → state update → debounce (750ms) → Discord update
```

**Phrase cooldown** — a random phrase must not change on every event (`phraseCooldownMs`, 5000ms), so
activity can change quickly without spamming personality.

> **Constraint**: `updateDebounceMs` alone does **not** satisfy Discord's rate limit — a hard
> throttle gate is still required — see §16.4.

## 16. Discord constraints & reality checks (verified)

These are non-negotiable and override any conflicting statement in the vision above. All are
verified in [`DISCORD-RPC.md`](./DISCORD-RPC.md).

### 16.1 The top line `name` is not reliably configurable

Discord renders `<Verb> <AppName>`. `AppName` = the **registered Discord Application name** from the
Developer Portal — not a config string. The Activity `name` field exists but is documented as
"usually omitted" and may be ignored over IPC. **To display "J.A.R.V.I.S.", name the Discord
Application "J.A.R.V.I.S.".** `identity.name` is best-effort only.

### 16.2 Discord has only two text lines

`details` (line 2) + `state` (line 3). There is no line 4. Telemetry (`150.4K (57%) • TODO 4/9`)
must be **merged into `state`**, or `party` used for TODO. Do not document a 4-line layout.

### 16.3 `party` for TODO is a semantic hack

`party` is designed for multiplayer party size and renders `(4 of 9)`. Repurposing it for TODO works
visually but is not its intent and needs runtime verification. Provide an alternative (append
`TODO 4/9` to `state`).

### 16.4 Rate limit is 5 updates / 20s

Discord allows **5 `SET_ACTIVITY` / 20s** → a hard floor of **≥4s between sends**. A 750ms debounce
alone violates this. Keep the throttle gate (`throttle.minIntervalMs: 4000`, existing option) in
addition to the debounce.

### 16.5 Activity `type` must be 0, 2, 3, or 5

Only `Playing (0)`, `Listening (2)`, `Watching (3)`, `Competing (5)` are valid over RPC.
`Streaming (1)` and `Custom (4)` are **invalid**. For opencode, **`Playing (0)` is recommended**
(conventional for dev tools); `Listening (2)` is the only "Spotify-like" option.

### 16.6 Timestamps use Unix seconds

For IPC `SET_ACTIVITY`, `timestamps.start` is **Unix seconds** (`Math.floor(Date.now()/1000)`), not
milliseconds.
